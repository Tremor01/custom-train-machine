# Серверное обучение и распознавание — дизайн

## Цель

Добавить в «Мастерскую распознавания» два режима с серверным извлечением признаков и обучением:

1. Обучать модель на сервере, затем распознавать поток камеры в браузере.
2. Обучать модель на сервере и отправлять кадры камеры на сервер для предсказания.

Пользователь работает один. Наборы примеров часто меняются, поэтому обучение запускается явно по кнопке, а не при каждом изменении набора.

## Текущая база

Клиент — Vite-приложение на TensorFlow.js 4.22 и MobileNet V2. `train()` последовательно прогоняет каждый пример через MobileNet (`infer(image, true)`), собирает embedding размера 1280 и обучает небольшую Dense-голову (64 скрытых узла, 25 эпох). `predictLoop()` на каждом проходе обрабатывает видео MobileNet и обученную голову. Примеры передаются как data URL; базовые веса MobileNet лежат в `public/models/mobilenet`.

## Предлагаемая архитектура

- Сохранить JavaScript/Node.js и текущие TensorFlow.js/MobileNetV2. Серверная CPU-реализация использует `@tensorflow/tfjs-node`; GPU не является требованием первой версии.
- Добавить Fastify API к существующему Vite-клиенту. В разработке Vite проксирует `/api` на API-процесс; production раздаёт клиент и API под одним origin.
- Сервер загружает базовую MobileNet один раз, принимает набор классов/изображений, обрабатывает изображения и обучает ту же Dense-архитектуру. Входное преобразование должно совпадать с клиентским путём, чтобы предсказания одной модели были сопоставимы на WebGL/WASM и серверном backend.
- Обученная модель состоит из сериализуемой Dense-головы и манифеста совместимости; она не включает базовые веса MobileNet. Манифест фиксирует embedding `[N, 1280]`, порядок классов, версию/конфигурацию MobileNet V2 и preprocessing. Браузер загружает совместимую MobileNet и голову; серверный inference использует тот же контракт.
- Обучение выполняется как единственная фоновая задача процесса с идентификатором, прогрессом по подготовке примеров и эпохам, а также состояниями queued/running/completed/failed. Для одного пользователя достаточно сериализовать обучение и серверный inference. Поскольку вычислительные операции TFJS Node могут синхронно блокировать event loop, ML исполняется в worker thread/отдельном worker-процессе, а не в обработчике Fastify. Не вводить внешнюю очередь/БД в первой версии.
- После обучения сервер сохраняет версионированный TensorFlow.js LayersModel и метаданные классов. Режим клиентского предсказания получает модельные артефакты по HTTP; клиент продолжает использовать базовую MobileNet и переданную Dense-голову.
- Режим серверного предсказания оставляет базовую MobileNet и обученную голову загруженными на сервере. Браузер отправляет JPEG-кадры с одним запросом одновременно, получает вероятности/класс и отображает существующие эффекты. Частоту отправки ограничить завершением предыдущего запроса, чтобы не копить устаревшие кадры.
- Результаты обучения, загруженные картинки и модель хранятся локально на VPS. В первой версии есть один активный пользователь и одна активная модель; данные не становятся публичными, изображения/артефакты не загружаются во внешнее хранилище.

## API и поток данных

- `POST /api/train`: multipart набор примеров с полями `classes` (JSON метаданных/порядка классов) и файловыми изображениями. Ответ — `jobId`.
- `GET /api/train/:jobId`: состояние и актуальные прогресс/метрики; по завершении возвращает идентификатор сохранённой модели.
- `GET /api/models/:modelId/model.json` и бинарные веса: TFJS LayersModel-формат, который загружается в браузере через `tf.loadLayersModel`.
- `POST /api/predict/:modelId`: один JPEG кадр; ответ содержит вероятности по упорядоченным классам. Клиент обеспечивает отсутствие параллельных запросов и может отбрасывать кадр, если предыдущий ещё в работе.

API ограничивает количество и общий размер изображений, разрешённые форматы, число/имена классов, размер кадров и общий объём запроса. Ошибки валидации возвращаются как понятные 4xx; ошибка/отмена задачи очищает временные файлы и освобождает тензоры. Модельные id генерируются сервером, а не берутся из пути клиента. Новая версия публикуется атомарно только после успешного обучения; после рестарта сервер восстанавливает активную модель с диска либо явно сообщает, что модель отсутствует/повреждена.

## Ускорение и измеримость

- Первая оптимизация: инструментировать этапы (приём/декодирование, MobileNet embedding, обучение головы, предсказание, сериализация/сеть), а не менять модель наугад.
- На сервере переиспользовать загруженную MobileNet и держать последнюю обученную модель в памяти. Примеры часто меняются, поэтому кэшировать признаки между наборами не требуется; в рамках одного запуска допустима пакетная обработка только если профиль и память это подтверждают.
- Для браузерного распознавания измерять холодный и прогретый inference; использовать асинхронное чтение результата TensorFlow.js и обновлять DOM с частотой, нужной интерфейсу, а не обязательно на каждом кадре.
- Для серверного распознавания ограничить входной размер/частоту кадров. Не обещать конкретные FPS до измерения RTT и времени модели на целевом VPS/соединении.
- Сравнить CPU backend на одной машине. Вариант GPU отдельный: `tfjs-node-gpu` требует совместимой Linux/NVIDIA/CUDA среды и не входит в обязательный запуск.

## Ошибки и эксплуатация

- Сервер не принимает кадры или проекты без явной пользовательской операции; клиентский режим не отправляет видео.
- На одну инсталляцию допускается один активный job; повторный запрос обучения во время job получает конфликт с текущим состоянием.
- Временные файлы и устаревшие версии модели удаляются после завершения/замены, оставляя актуальную сохранённую модель. Ограничить disk/RAM через лимиты на вход и набор.
- В production API и сайт работают за HTTPS под одним origin. API не имеет встроенной авторизации; доступ ограничивается сетевым firewall/VPN или аутентифицированным reverse proxy. Не оставлять незакрытый порт доступным из публичного интернета.

## Тестирование и критерии готовности

- Unit-тесты валидации набора, модели/job state и backend-функций.
- API-тест: загрузить маленький синтетический набор, дождаться job, проверить метрики/артефакты, загрузить модель клиентом и получить предсказание.
- Интеграционный тест обоих режимов: браузерная модель выдаёт ожидаемую форму вероятностей; server prediction принимает кадр и возвращает конечные вероятности с теми же метками/порядком. На одном тестовом кадре сравнить client/server выходы с допуском, проверяя совпадение декодирования, RGB, размера, нормализации и версии extractor.
- Проверить ошибочные файлы, превышение лимитов, повторный job, освобождение тензоров, перезапуск сервера и отсутствие активной модели.
- `npm test`, build и тестовый запуск API; провести benchmark с реальным MobileNet-набором отдельно для холодного старта, feature extraction, обучения головы и inference. До появления результатов численные требования к CPU/GPU/FPS не фиксируются.

## Альтернативы

- Python/FastAPI + PyTorch: не выбрано, потому что требует переписать MobileNet feature extraction и обеспечить точное совпадение препроцессинга/экспорта с браузерным TFJS.
- Только браузерное обучение с серверной раздачей: не удовлетворяет требованию снять вычислительную нагрузку с любых пользовательских устройств.
- Серверное обучение с клиентской и серверной головой без общей TFJS-формы: повышает риск несовпадающих выходов. Сериализуемая TFJS LayersModel позволяет использовать одну обученную голову в обоих режимах.

## Границы первой реализации

Один пользователь, один API-процесс, один активный job/модель, CPU backend, MobileNetV2 без замены, хранение на локальном диске VPS. Без multi-tenant, внешней очереди, S3, автономного обучения при каждом изменении примеров и серверной записи аудио/видео.
